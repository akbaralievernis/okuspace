## 2. Инварианты, закреплённые в БД

| Правило | Механизм |
|---|---|
| Данные не смешиваются между организациями | `organization_id NOT NULL` + составные FK `(organization_id, branch_id[, id])` + запрет менять эти столбцы (`forbid_column_change`) |
| Директор — на всю организацию; филиальные роли — строго с филиалом | CHECK `memberships_director_scope_check`, `memberships_branch_required_check` |
| Нет дубля активной роли | уникальный индекс `memberships_unique_active_idx` (`NULLS NOT DISTINCT`) |
| Уровень принадлежит языку курса; CEFR — только A1–C2 | составной FK `courses_level_fkey`, CHECK `course_levels_cefr_check` |
| Нет повторной записи в группу; вместимость группы | частичный уникальный индекс + триггер `check_enrollment` с `FOR UPDATE` |
| Нет двойного бронирования преподавателя и аудитории | `EXCLUDE USING gist (… WITH =, period WITH &&) WHERE status <> 'cancelled'` |
| Занятие ведёт только преподаватель группы; аудитория — того же филиала | триггер `check_lesson_session`, составной FK |
| Одна работа на ученика и задание; оценка ≤ `max_score`; ученик не оценивает себя | UNIQUE + триггер `guard_submission` |
| Деньги — `numeric(14,2)`, сумма > 0, валюта ISO 4217 | типы + CHECK |
| Платежи и распределения нельзя изменить или удалить (даже service role); счёт нельзя удалить | триггеры `forbid_mutation` на UPDATE/DELETE/TRUNCATE |
| Возврат ссылается на исходный платёж, имеет причину и не превышает нераспределённый остаток | CHECK + триггер `check_payment` |
| Распределение не превышает ни платёж, ни счёт | триггер `check_allocation` |
| Повторное событие провайдера не создаёт второй платёж | `UNIQUE (provider, provider_ref)` |
| Выставленный счёт только аннулируется (с причиной) | триггер `guard_invoice` |
| Журнал аудита append-only; хеши токенов в него не попадают | триггеры `forbid_mutation`, `audit_row` (`diff - 'token_hash'`) |

|---|---|---|---|---|---|---|---|
| `profiles` | R свой + преподаватели своих групп | R ребёнка + его преподавателей | R учеников своих групп | R в охвате (`member.read`) | R в охвате | R вся организация | — |
| `profile_private` | R/W свой | R ребёнка | — | R в охвате | R в охвате | R | — |
| `memberships` | R свои | R свои | R свои | R/W в охвате, только по `role_grants`, **не свои** | R в охвате | R/W (кроме `org_director`) | — |
| `groups`, `lesson_sessions` | R своих групп | R групп ребёнка | R своих групп | R/W в охвате | R | R/W | — |
| `enrollments` | R свои | R ребёнка | R своих групп | R/W в охвате | R | R/W | — |
| `assignments` | R опубликованные своих групп | R опубликованные групп ребёнка | R/W своих групп | рук. филиала: R (`learning.read_all`) | — | R | — |

Владелец платформы (`platform_admins`) управляет организациями: создание, приостановка. Данные школ он через RLS не читает. Записи в `platform_admins` и справочники RBAC делаются только миграциями или через service role.

Роль `anon` не имеет привилегий ни на одну таблицу. Функции схемы `app` для `anon` и `PUBLIC` не исполняемы.

## 4. Функции прав (схема `app`, `SECURITY DEFINER`, `search_path = ''`)

| Функция | Что проверяет |
|---|---|
| `is_platform_admin()` | текущий пользователь — владелец платформы |
| `is_member(org)` | активное членство в активной организации |
| `has_permission(org, branch, perm)` | право через роль. `branch = null` — ресурс уровня организации, подходят только членства без филиала |
| `can_assign_role(org, branch, role)` | `member.manage` + `role_grants` + охват |
| `staff_can(profile, perm)` | право над участником в охвате его членства |
| `is_guardian_of(student)` | активная связь опекунства + активное членство родителя |
| `is_group_teacher` / `is_group_student` / `is_group_guardian` / `can_read_group(group)` | связь с группой |
| `can_see_profile(profile)` | объединение правил видимости профиля |

Все функции работают только относительно `auth.uid()`: узнать с их помощью права другого пользователя нельзя.

## 7. Обучение: контент, тесты, прогресс (этап 5)

**Кто что видит и меняет**

| Действие | Кто |
|---|---|
| Править структуру курса, уроки, тесты | `catalog.manage` в организации или преподаватель группы этого курса (`app.can_edit_course`) |
| Видеть опубликованные уроки и тесты | ученик активной записи на группу курса и его родитель, преподаватель курса, сотрудник с `learning.read_all` |
| Видеть ключи ответов (`assessment_answer_keys`) | только редакторы курса. Ученику таблица недоступна целиком |
| Назначать тест группе, давать пересдачу | преподаватель группы (тест должен быть опубликован и относиться к курсу группы) |
| Отправлять попытку | только сам ученик, через `submit_assessment_attempt` (прямой INSERT закрыт) |
| Видеть попытки и разбор | сам ученик, его родитель, преподаватель группы, сотрудник с правом на результаты (`app.can_view_student_results`) |

**Попытки.** `submit_assessment_attempt(assessment, answers, idempotency_key)`:

- проверяет окно назначения и лимит попыток (`max_attempts` + пересдачи);
- оценивает ответы на сервере по ключам: `gap_fill` даёт частичный балл, текст сравнивается после нормализации;
- записывает попытку сразу с итоговым баллом, потом ответы. Обе таблицы append-only;
- повтор с тем же ключом возвращает ту же попытку, а не создаёт новую. Номер попытки уникален, параллельные отправки сериализуются advisory-блокировкой.

**Показ ответов** (`attempt_review`) зависит от `reveal_answers` теста:

- `never` — ключи и пояснения ученику не показываются;
- `after_submit` — сразу после попытки;
- `after_due` — после срока назначения группы.

Редакторы курса видят ключи всегда. Вопросы и ключи с уже данными ответами менять нельзя (`app.guard_answered_question`), чтобы старые результаты оставались верными.

**Прогресс.** `course_progress` считается из сохранённых строк `lesson_progress` и `assessment_attempts`, отдельного счётчика нет. Завершённый урок повторным открытием не «откатывается».

Тесты — `tests/security/lms.test.ts` (26), включая полный сценарий «запись → урок → тест → разбор → прогресс».

**Занятия.** Двойное бронирование преподавателя и аудитории запрещают EXCLUDE-ограничения (с этапа 2); отменённые занятия слот не занимают. `create_session_series` создаёт серию по дням недели в поясе филиала (`(дата + время) at time zone пояс` — корректно при переходе на летнее время) одной транзакцией: конфликт хотя бы одного занятия откатывает всю серию и называет дату. `session_conflicts` объясняет конфликт: вид (преподаватель / аудитория) и время; название группы — только если она видна вызывающему.

Отменённое занятие изменить нельзя, проведённое — перенести.

**Посещаемость**

| Источник | Как попадает | Становится отметкой |

| Преподаватель | `mark_attendance` с 15 минут до начала до 48 часов после конца | да |

## 9. AI Language Lab (этап 7)

**Выключено по умолчанию.** AI работает, только если на сервере настроен провайдер (`AI_PROVIDER=anthropic` + ключ) **и** школа включила его в `ai_settings` (право `ai.manage`, MFA). Иначе AI-страницы показывают понятное сообщение, а уроки, тесты и домашние задания работают как обычно — они от AI не зависят.

**Лимиты и бюджет — в БД.** `ai_begin` под advisory-блокировкой школы проверяет: членство, включённость, ≤ 6 вызовов в минуту и дневной лимит на человека, месячный бюджет (факт + резерв незавершённых вызовов за 15 минут). Резерв — оценка максимальной стоимости вызова; после ответа `ai_finish` записывает фактические токены и стоимость в микродолларах (целые числа). `ai_finish` доступна только service role: пользователь не может «удешевить» вызов или закрыть его за сервер. Закрытый вызов неизменен.

**Приватность.** Диалоги видит только владелец (родитель и преподаватель — нет); реплики ассистента и AI-отзывы пишет только сервер. **Оспаривание.** Любой AI-отзыв может оспорить ученик или преподаватель группы (один спор на человека). Решение («AI ошибся» / «оценка верна») с обязательным комментарием принимает преподаватель или руководство, один раз; суть спора не меняется; всё пишется в аудит.

**Упражнения** проверяет БД (`record_practice`) по сохранённым ответам той же нормализацией, что тесты LMS, — модель в проверке не участвует.

## 10. CRM (этап 8)

**Без дублей.** Телефон приводится к единому виду (`app.normalize_phone`: «0555 12-34-56» → `+996555123456`), email — к нижнему регистру. Уникальные индексы: один телефон и один email — один контакт школы (обезличенные не считаются). Запись на курс — `crm_enroll` (право `enrollment.manage` в филиале группы; вместимость проверяет триггер этапа 2).

Изменения — `lead.manage` + MFA; менеджером и исполнителем напоминания можно назначить только сотрудника продаж этого филиала. Преподаватели, бухгалтеры, ученики и другие школы контакты не видят.

## 11. Финансы (этап 9)

**Деньги** — только `numeric(14,2)` + ISO 4217 (инвариант схемы проверяется тестом для всех столбцов `amount`/`total`). Сервер приложения передаёт суммы строками; функции БД с неограниченным `numeric` отклоняют больше двух знаков после точки (`p <> round(p, 2)`).

**Счёт.** Черновик со строками: цена строки с тарифом берётся из прайс-листа (ручная цена заменяется), сумма счёта = Σ строк − утверждённые скидки — её считает БД, ручная правка суммы перезаписывается. Выставление — без неутверждённых скидок; выставленный счёт меняется только аннулированием (без оплат). К оплате (`due`) = сумма + утверждённые дебет-ноты − утверждённые кредит-ноты. Каждая смена статуса — строка `invoice_status_history`.

**Утверждение (четыре глаза).** Скидку (на черновик) и кредит/дебет-ноту (на выставленный счёт) запрашивает бухгалтер (`finance.write`), утверждает или отклоняет другой человек с `finance.approve` — один раз. CHECK `decided_by <> requested_by`. Кредит не может превышать неоплаченную часть: чтобы уменьшить оплаченный счёт, сначала освобождается распределение.

**Платежи и возвраты.** Распределение платежа на счёт не превышает остатков платежа и счёта; освобождение (`release`, с причиной, право `finance.refund`) возвращает деньги в свободный остаток платежа; возврат — только из свободного остатка. Ничего не обновляется и не удаляется.

**Периоды.** Закрытый месяц (в поясе школы) не принимает платежей, возвратов, распределений, расходов, корректировок, выставления и аннулирования. Закрывает и открывает (с причиной) `finance.approve` уровня школы; всё в аудите.

**Онлайн-оплата.** `record_provider_payment` (только service role) пишет событие провайдера в `payment_webhook_events` (уникально `(provider, event_id)`), повтор события или той же операции провайдера (`payments_provider_ref_key`) возвращает уже записанный платёж; распределяет не больше остатка счёта. Данные карт платформа не получает.

**Отчёты.** `finance_report(org, from, to)` по филиалам и валютам: выставлено, получено, возвращено, расходы (с учётом сторно), задолженность; `finance_debts(org)` — плательщики с остатком. Только охват `finance.read`.

**Права.** Бухгалтер: счета, строки, запросы корректировок, платежи, возвраты, освобождения, расходы. Директор и менеджер филиала: утверждения, прайс-листы, периоды, чтение. Директор не проводит деньги сам; бухгалтер не утверждает.

Тесты — `tests/security/finance-module.test.ts` (16) и `finance.test.ts` (этап 2).

## 14. Управление филиалами (блок A)

**Задачи.** Одна задача — один исполнитель. Рассылка в несколько филиалов создаёт несколько задач с общим `batch_id`: каждая выполняется, сдаётся и принимается отдельно, а руководитель видит прогресс всей рассылки.

| Действие | Кто | Условия |
|---|---|---|
| поставить (`task_create`) | `task.manage` в филиале задачи, MFA | исполнитель — активный сотрудник этого филиала (менеджер, администратор, продажи, бухгалтер, преподаватель) или сотрудник уровня школы для задачи уровня школы; не сам автор; срок в будущем; до 50 исполнителей |
| взять в работу / сдать отчёт | исполнитель | `open → in_progress`; сдача из `open`/`in_progress` только с отчётом |
| принять / вернуть / отменить | автор задачи или директор школы, MFA | `task.manage` в филиале задачи; **не исполнитель** (даже если позже получил права уровня школы); возврат — с комментарием, отмена — с причиной |
| комментарий | исполнитель или руководитель охвата (MFA) | уведомляется другая сторона |

Каждый шаг пишется в `staff_task_events` (append-only, запрет даже для service role). Просроченные (`open`/`in_progress` со сроком в прошлом) — одно напоминание исполнителю и одно автору (`generate_task_reminders`, планировщик).

**Видимость.** Задачу видят исполнитель и `task.manage` в её филиале: менеджер филиала видит задачи своего филиала, директор — все.

**Объявления.** Адресуются филиалу (или всей школе — только уровень школы) и ролям получателей. Получатели фиксируются при публикации (`announcement_recipients`, `recipient_count`); автор в получатели не входит; без получателей публикация отклоняется. После публикации текст, адресаты и автор неизменны (триггер); удалить нельзя — только в архив (автор или директор). Получатель видит свою квитанцию; открытие страницы отмечает «прочитано», подтверждение — отдельным действием и только если оно запрошено. Статистику (`announcement_stats`) и список квитанций видят только те, кто публикует в охвате объявления.

**Панель (`branch_dashboard(org, from, to)`).** Филиалы с `dashboard.read`. Период — даты по часовому поясу школы, включительно.

| Показатель | Определение |
|---|---|
| ученики | разные ученики с активной записью в группы филиала (на сегодня) |
| группы / преподаватели | группы `planned`/`active`; разные преподаватели этих групп |
| занятия | по началу в периоде: `planned` = не отменённые, `done`, `cancelled` |
| без отметок | прошедшие неотменённые занятия периода без единой отметки посещаемости |
| посещаемость | `present`+`late`+`left_early` / все отметки, кроме `excused` |
| работы ждут проверки | `submitted` (на сегодня); просрочены — сданы > 72 ч назад |
| обращения | контакты CRM филиала, созданные в периоде; из них `won` (как `crm_funnel`) |
| задачи | открытые (`open`/`in_progress`/`submitted`) и просроченные на сегодня; выполнены — `completed_at` в периоде |
| объявления | подтверждения по объявлениям периода с запросом подтверждения |
| финансы | только при `finance.read` в филиале; поступило/возвраты — как `finance_report`; долг — остаток выставленных счетов; просрочен — со сроком до сегодня |

Тесты сверяют каждый показатель с прямым запросом к данным, а финансы — с `finance_report`.

Тесты — `tests/security/management.test.ts` (17), unit — `tests/unit/management/period.test.ts` (4).

## 15. Оценивание и итоги месяца (блок B)

**Задания отдельным ученикам.** Если у задания есть строки в `assignment_students`, его видят, сдают и получают о нём уведомление только эти ученики и их родители; иначе — вся группа. `assignment_create` создаёт черновик, записывает адресатов (только активные ученики группы) и публикует — уведомления уходят уже с учётом адресатов. Сдать неадресованное задание нельзя (триггер).

**Экзамены.** `group_exams` — экзамен в классе (дата, максимум). Баллы вносит преподаватель группы: не больше максимума, только ученикам группы, «не пришёл» — без балла. Ученик и родитель видят свой результат только после публикации. Опубликованный экзамен нельзя снять с публикации, удалить или изменить максимум; исправление балла пишется в аудит (экзамен, ученик, было → стало). Онлайн-тест группы можно засчитать как экзамен (`counts_as_exam`).

**Правила (`grading_policies`).** Веса четырёх частей (целые, сумма 100) и шкала (`five` / `percent`). Без строки — 20/30/20/30, пятибалльная. Меняет директор с MFA.

**Расчёт (`app.compute_report`)** — по ученику, группе и месяцу (границы — по часовому поясу школы):

| Часть | Определение |
|---|---|
| посещаемость | (`present` + `late` + `left_early`) / все отметки, кроме `excused`, по занятиям группы, начавшимся в месяце |
| домашние | задания группы (адресованные ученику) со сроком — или датой выдачи, если срока нет — в месяце: проверено → балл/максимум; не сдано после срока → 0; сдано, не проверено → не учитывается |
| тесты | тесты группы (не «экзамен») со сроком — или датой открытия — в месяце: лучшая попытка; без попытки после срока → 0; до срока → не учитывается |
| экзамены | опубликованные экзамены месяца (не пришёл → 0, балл не внесён → не учитывается) и тесты «как экзамен» по правилу тестов |
| итог | Σ(вес × часть) / Σ(весов частей, где есть данные); пятибалльная: ≥ 90 → 5, ≥ 75 → 4, ≥ 60 → 3, иначе 2 |

**Табель (`report_cards`).** `report_cards_generate(group, month)` (преподаватель группы или `group.manage`) пересчитывает черновики всех учеников и сохраняет комментарий; опубликованные не трогает. В снимке — части, итог, оценка, использованные веса и счётчики. `report_cards_publish` публикует черновики: ученик и родители получают уведомление. Опубликованный табель неизменен (триггер, в том числе для service role). `generate_monthly_reports` (планировщик) 1–3 числа создаёт черновики за прошлый месяц для групп, у которых в том месяце были занятия, и уведомляет преподавателей.

**Видимость.** Табели и результаты видят преподаватель группы и `learning.read_all` в филиале; ученик и родитель — только опубликованное и только своё.

Тесты — `tests/security/grading.test.ts` (11): каждая часть сверена с посчитанными вручную значениями, unit — `tests/unit/management/month.test.ts` (3).
