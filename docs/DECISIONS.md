## ADR-0001 · Чистый старт вместо рефакторинга PHP-портала

- **Дата:** 2026-10-15
- **Статус:** принято пользователем («удали всё и начни с начала; если необходимо — оставь»)
- **Контекст:** аудит этапа 0 (локальный `docs/audit/PROJECT_AUDIT.md`, не публикуется) показал:
  - текущий код — PHP-портал университетской группы;
  - другая предметная область, другой стек;
  - 0 внешних ключей в схеме, критические уязвимости;
  - 1 учётная запись в production.
- **Решение:**
  1. Перед удалением сделана полная локальная резервная копия `htdocs` → `C:\Users\user\Desktop\okuspace-htdocs-backup-2026-10-15.zip`. В ней 296 файлов; целостность проверена: SHA-256 каждого файла совпадает с оригиналом, `testzip` прошёл.
  2. Из `htdocs` удалено всё, кроме `docs/` (аудит) и `.claude/` (локальные настройки инструмента). Отчёт аудита `docs/audit/` хранится только локально и исключён из git: репозиторий публичный.
  3. Okuspace Next строится в `htdocs` с нуля на Next.js + Supabase.
  4. Данные старого портала **не мигрируются**. Учебный контент DeutschBlitz (видео, субтитры, словарь) и словари интерфейса KG/RU остаются в архиве как референс. Права на видео — **[ВОПРОС]**.
- **Последствия:**
  - Этапы миграции данных из отчёта аудита (локальный `docs/audit/DATA_INVENTORY.md`) больше не нужны. Резервную копию production-БД всё равно стоит снять перед отключением старого сайта.
  - Старый сайт деплоится из отдельного репозитория и этим решением не затронут. Меры по нему описаны в локальном отчёте аудита; решение за владельцем.
  - Архив содержит секреты старого проекта. Хранить его локально и никуда не загружать. Секреты нужно ротировать в любом случае.

## ADR-0004 · Тестовая БД для миграций и RLS — PGlite

- **Дата:** 2026-10-15
- **Статус:** принято на этапе 2 (вариант 3 из [TESTING_STRATEGY §2](architecture/TESTING_STRATEGY.md)); пересматривается, когда появится Docker или тестовый проект Supabase
- **Контекст:** на машине нет Docker, поэтому `supabase start` недоступен. Тестового облачного проекта Supabase пока нет.
- **Решение:** dev-зависимость `@electric-sql/pglite@0.5.8` — настоящий PostgreSQL 18.3, скомпилированный в WASM, с расширением `btree_gist`.
  - Перед миграциями применяется `tests/db/supabase-shim.sql` (только для тестов): роли `anon`, `authenticated`, `service_role`, схема `auth`, `auth.users`, `auth.uid()` и `auth.jwt()` из `request.jwt.claims` — так же, как в Supabase.
  - Запросы от имени пользователя выполняются через `SET LOCAL ROLE authenticated` + claims, то есть так, как это делает PostgREST.
  - Пробный запуск подтвердил, что RLS, `SET ROLE` и EXCLUDE-ограничения работают.
- **Ограничения (остаточный риск):**
  1. Supabase в production работает на PostgreSQL 15–17, а PGlite — на 18.3. Используются только возможности, доступные с PG15 (`NULLS NOT DISTINCT` — PG15).
  2. Shim повторяет только нужную часть Supabase. Реальные Auth, Storage, PostgREST и default privileges Supabase не проверены.
  3. **До staging/production миграции обязательно прогоняются на настоящем Supabase**: локально через Docker или на тестовом проекте, тем же набором `tests/security`.
- **Почему не облачный тестовый проект сразу:** для него нужны аккаунт и ключи пользователя. PGlite не требует внешней инфраструктуры и работает в CI без секретов.

## ADR-0005 · Публичный сайт управляется данными; аноним — только через public_* RPC

- **Дата:** 2026-10-16
- **Статус:** принято на этапе 4
- **Контекст:** реальных материалов школы (тексты, цены, преподаватели, юридические документы) нет, а мастер-промпт запрещает фиктивные данные. Публичным страницам нужен анонимный доступ к части данных, но этап 2 закрепил правило «у anon нет привилегий ни на одну таблицу».
- **Решение:**
  1. Все публичные данные берутся из БД. Страницы «О школе / Контакты / FAQ» и юридические документы редактирует директор в кабинете (`site.manage` + MFA). Юридические документы версионируются, опубликованная редакция неизменна.
  2. Аноним читает только через 7 функций `public_*` (`SECURITY DEFINER`). Они отдают опубликованное без персональных полей. Тест проверяет, что anon может вызвать только функции `public_*`.
  3. Пока не опубликованы политика конфиденциальности и правила, регистрация и приём заявок закрыты. Согласие записывается на конкретную опубликованную версию документов конкретной школы.
  4. Заявки с сайта сохраняются только сервером (service role) через `submit_lead_request()`. Действуют: идемпотентность (ключ дедупликации), вместимость слота, проверка версии согласия, лимиты, поле-ловушка для ботов.
  5. Преподавателя публикует только он сам — это его согласие. Руководство может только снять профиль с публикации.
- **Последствия:** до наполнения контентом сайт показывает честные пустые состояния. Курсы и цены публикуются через БД (SQL) до этапа 5, где появится управление каталогом.

## ADR-0007 · LMS: проверка тестов в БД, ключи отдельно, идемпотентные попытки

- **Дата:** 2026-10-16
- **Статус:** принято на этапе 5
- **Решение:**
  - ответы проверяет функция PostgreSQL `submit_assessment_attempt`, а не приложение: клиент не может прислать свой балл;
  - ключи хранятся в отдельной таблице `assessment_answer_keys`, которую ученик не читает вообще (RLS по строкам здесь не нужен — таблица закрыта целиком). Варианты ответов в `assessment_questions` не содержат признака правильности;
  - когда показывать ответы, решает `attempt_review` по правилу теста (`never` / `after_submit` / `after_due`);
  - ключ идемпотентности генерирует сервер при показе формы. Двойная отправка той же формы возвращает ту же попытку;
  - медиа уроков — внешние https-ссылки (`media-src https:` в CSP). Встраивание сторонних плееров (`frame-src`) не разрешено; загрузка файлов в Supabase Storage — отдельной задачей вместе с антивирусной проверкой и квотами.
- **Альтернатива:** проверка в Server Action по ключам, прочитанным service role. Отклонено: логика оценивания и прав разошлась бы с RLS, а service role в пользовательском запросе расширяет поверхность атаки.
- **Ограничение:** таймеры тестов и ручная проверка открытых ответов (эссе, устная речь) не реализованы. Письменные и устные задания сдаются как домашние работы.

## ADR-0008 · Посещаемость: доказательства отдельно от отметок, человек подтверждает камеру

- **Дата:** 2026-10-16
- **Статус:** принято на этапе 6
- **Решение:**
  - события устройств и кодов (`attendance_events`) хранятся как неизменяемые доказательства; подтверждённая отметка (`attendance_records`) — одна на «занятие + ученик», каждая её версия — в истории;
  - событие камеры никогда само не становится отметкой: её создаёт преподаватель или сотрудник, и запись хранит, кто подтвердил;
  - все записи отметок — через функции БД (окна отметки, проверка записи ученика в группу, причина исправления), прямой записи в таблицы нет;
  - уведомления об изменениях расписания создаёт триггер БД в той же транзакции, что и изменение: изменение без уведомления невозможно, повтор не создаёт дубль. Доставка во внешние каналы (email, мессенджеры) — очередь этапа 11;
  - неверный код занятия возвращает `null`, а не исключение, — иначе откат транзакции обнулял бы счётчик попыток.
- **Альтернатива:** одна таблица «отметок» с полем источника и флагом «подтверждено». Отклонено: подтверждение задним числом меняло бы доказательство, а история смешивала бы сырые события и решения людей.
- **Ограничение:** интеграции карт и камер (серверный приёмник событий, учёт устройств) — этапы 10–11; сейчас есть только функция приёма для service role.

## ADR-0009 · AI Language Lab: провайдер за интерфейсом, лимиты в БД, голос выключен

- **Дата:** 2026-10-16
- **Статус:** принято на этапе 7
- **Решение:**
  - единый интерфейс `AiProvider` (`src/server/ai/types.ts`); реализация — Anthropic Claude через официальный SDK `@anthropic-ai/sdk@0.135.0`. Модель по умолчанию — `claude-opus-5-5` (переменная `AI_MODEL`), структурированный вывод через Zod-схемы, серверный fallback при отказе модели (`fallbacks: "default"`), тайм-аут на каждый запрос, одна повторная попытка SDK;
  - ключ — только серверная переменная; SDK не попадает в клиентскую сборку (проверка `check:bundle` ищет и имя переменной, и формат ключа `sk-ant-…`);
  - AI выключен по умолчанию на двух уровнях: сервер (`AI_PROVIDER=none`) и школа (`ai_settings.enabled = false`); без AI обучение работает полностью;
  - бюджет и лимиты проверяет БД, а не приложение: резерв до вызова, фактическая стоимость после, закрытие вызова — только service role;
  - качество: каждый ответ проходит схему и проверку `vetWritingCheck` (исправление засчитывается, только если исходный фрагмент целыми словами есть в тексте ученика); ненадёжный ответ не показывается. Набор тестовых примеров и платный прогон `npm run eval:ai`;
  - модель не оценивает акцент, произношение и уровень (это запрещено в промптах и сказано в интерфейсе); любая AI-оценка оспаривается и разбирается преподавателем;
  - **голос:** запись и распознавание речи не реализованы и выключены (`voice_enabled = false`). Для них нужны выбор сервиса распознавания речи, уведомление и правовое основание (закон КР о персональных данных). Озвучивание реплик — синтезатором браузера, только локальными голосами.
- **Альтернатива:** вызов API напрямую через `fetch` без SDK. Отклонено: типизированные ошибки, тайм-ауты и разбор структурированного вывода уже есть в SDK.
- **Ограничение:** реальное качество отзывов на выбранной модели не измерено (нет ключа и согласия на расход) — прогон `eval:ai` обязателен до включения AI для школ.

## ADR-0010 · CRM поверх заявок сайта; дубли и история — в БД; экспорт и удаление — отдельное право

- **Дата:** 2026-10-16
- **Статус:** принято на этапе 8
- **Решение:**
  - `lead_requests` (этап 4) остаются неизменяемым «входящим» с согласием на конкретную версию политики; рабочая сущность — `crm_contacts`. Заявка сайта сразу связывается с контактом (новым или существующим) в той же транзакции;
  - защита от дублей — нормализация телефона/email и уникальные индексы в БД, а не проверка в интерфейсе;
  - история этапов и менеджеров пишется триггером; события общения — append-only, допускается только обезличивание;
  - новое право `crm.admin` (директор, менеджер филиала, MFA) на экспорт и удаление по запросу; менеджеры по продажам работают с контактами, но не выгружают базу и не удаляют её;
  - срок хранения необработанных контактов — 24 месяца без активности, затем обезличивание (запуск по расписанию — этап 13). Срок подтверждён пользователем 2026-10-16; до публичного запуска его должен проверить юрист.
- **Альтернатива:** одна таблица заявок, расширенная полями CRM. Отклонено: заявка с сайта — юридический факт (согласие на версию политики), её не следует переписывать, а у одного человека бывает несколько заявок.

## ADR-0011 · Финансы: расчёты в БД, утверждение вторым лицом, общий HMAC-webhook

- **Дата:** 2026-10-16
- **Статус:** принято на этапе 9
- **Решение:**
  - все суммы, остатки, лимиты и запреты считает PostgreSQL (`numeric`), приложение передаёт строки и показывает результат; арифметика в интерфейсе — целыми копейками (`BigInt`), без `number`;
  - исправления — только новыми связанными записями: скидка/кредит/дебет-нота, освобождение распределения, возврат, сторно расхода; удаление и правка финансовых записей запрещены триггерами;
  - разделение обязанностей: бухгалтер записывает, руководитель утверждает (`finance.approve`), CHECK запрещает утверждать свой запрос;
  - онлайн-оплата: провайдер-независимый приём событий с подписью `HMAC-SHA256(secret, "<t>.<тело>")`, окном 5 минут против повторной отправки и идемпотентностью в БД. Конкретный провайдер подключается адаптером к этой схеме;
  - данные карт, CVV и платёжные секреты в БД не попадают; секрет webhook — только серверная переменная.
- **Ограничение:** платёжный провайдер не выбран (в КР — например, местные эквайеры и платёжные сервисы с подписью webhook). Нужны договор, тестовые ключи и формат их событий для адаптера.

## ADR-0012 · Мониторинг аудиторий: только числа, выключен до юридической проверки

- **Дата:** 2026-10-16
- **Статус:** принято на этапе 10 (базовый уровень)
- **Решение:**
  - платформа принимает от устройств только числа (сколько людей; вход/выход) — без изображений, видео, лиц и идентификаторов. Обработка видео (если она есть) остаётся внутри устройства или шлюза в сети школы; видеопоток в интернет и сторонним AI API не передаётся;
  - распознавание лиц, анализ эмоций и «оценка внимания» не реализуются и не планируются; идентификация ученика — только код занятия, карта доступа или преподаватель;
  - предупреждения — повод для проверки человеком; посещаемость автоматически не меняется, никто автоматически не наказывается;
  - выключено по умолчанию; включение требует цели, основания, опубликованного уведомления и отметки о юридической проверке (CHECK в БД);
  - отдельный секрет для каждого устройства (в БД только хеш), протокол `/api/monitoring/ingest` со строгой схемой;
  - каждый просмотр данных — запись в журнале доступа; ограниченный срок хранения с автоматическим удалением.
- **Альтернатива:** приём видео или кадров на сервер с распознаванием. Отклонено: избыточные персональные (в т. ч. биометрические) данные детей, юридический риск, нет подтверждённой точности.
- **Ограничение:** точность подсчёта зависит от устройства и установки — её нужно измерить на месте до того, как опираться на предупреждения (см. `docs/operations/MONITORING_CHECKLIST.md`).
