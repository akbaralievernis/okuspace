# Отчёт: Этап 11 — Автоматизация и уведомления

Дата: 2026-10-17. Ветка: `feat/stage-11-notifications` (от `feat/stage-10-monitoring`).

## 1. Что сделано

Уведомления создаются в базе данных по событиям и по расписанию, доставляются в кабинет сразу, а во внешние каналы — через очередь со статусами и ограниченными повторами ([ADR-0013](../DECISIONS.md), [SCHEMA.md §13](../database/SCHEMA.md)).

| Требование | Реализация |
|---|---|
| Напоминания о занятиях | планировщик: занятия в ближайшие 24 часа → ученики группы и преподаватель (`lesson_reminder`) |
| Уведомления о домашних заданиях | задание опубликовано → ученики группы; работа проверена или возвращена → ученик |
| Результаты тестов | попытка завершена → ученик и опекуны |
| Предупреждения об отсутствии | отметка «отсутствовал» → ученик и опекуны |
| Напоминания об оплате | за 3 дня до срока; после срока — раз в неделю (плательщик: ученик и опекуны) |
| Изменения расписания | перенос, отмена, другие изменения (этап 6; теперь и во внешние каналы) |
| Сообщения преподавателю о новых работах | работа сдана → преподаватели группы |
| Сигналы менеджеру о важных проблемах | второй пропуск подряд в группе → менеджер, администраторы филиала, директор; предупреждения мониторинга (этап 10) |
| Автоматические отчёты | еженедельный отчёт директору по понедельникам (время школы): новые контакты, записи, поступления, посещаемость, неудачные доставки |
| Каналы | кабинет (всегда); email (адаптер Resend); Telegram (бот, привязка одноразовым кодом) |
| Настройки пользователя | страница «Настройки уведомлений»: вид × канал; важное в кабинете не выключается |
| Статус доставки | у каждого уведомления в списке — статус по каналам: в очереди, отправляется, повтор, доставлено, не доставлено, пропущено |

**Очередь доставки.** Таблица `notification_deliveries` в Postgres:

- захват пачкой с `FOR UPDATE SKIP LOCKED`;
- до 5 попыток, задержка 2^n минут;
- зависшие доставки забираются снова через 10 минут;
- постоянные ошибки (4xx, нет канала, нет адреса) помечаются «пропущено», без повторов.

Обработчик запускает планировщик: `GET /api/cron/notifications` с `Authorization: Bearer CRON_SECRET`. Шаги независимы, сбой одного не отменяет остальные:

1. уведомления по расписанию;
2. доставка;
3. удаление по сроку хранения (мониторинг; контакты CRM без активности 24 месяца).

**Секреты** — только серверные переменные: `CRON_SECRET`, `RESEND_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`.

- `check:bundle` теперь ищет и эти имена.
- В журнал пишутся только коды ответов и имена переменных.
- Без настройки канал выключен: доставки помечаются «пропущено», основное действие не затрагивается.

## 4. Остающиеся проблемы и риски

1. **Провайдеры не выбраны и не подключены.** Реальная отправка email и Telegram не проверялась. Нужны домен отправителя (SPF/DKIM), ключ Resend (или другой провайдер), бот и `setWebhook` с секретом. Проверка — на staging.
2. **Частота планировщика.** В `vercel.json` — раз в сутки (02:00 UTC = 08:00 Бишкек): чаще план Vercel Hobby не позволяет. Пока так:
   - внешние доставки (пропуск, проверенная работа) приходят с задержкой до суток;
   - 5 попыток растягиваются на 5 дней.

   В кабинете уведомления появляются сразу. Для оперативной доставки нужен запуск каждые 5–10 минут — Vercel Pro или внешний планировщик (Supabase Cron, GitHub Actions) с тем же секретом.
3. **У Telegram нет ключа идемпотентности.** При сбое между отправкой и записью итога сообщение может прийти дважды. У email такой проблемы нет: ключ — id доставки.
4. Проверка занятий мониторингом (`monitoring_check`) по расписанию не запускается; удаление по сроку уже в планировщике. Предупреждение «устройство не передаёт данные» не сделано (этап 13).
5. Отрисовка страниц с данными (список и настройки) в браузере не проверена: в e2e нет БД.
6. Письма — только текст, без ссылки «отписаться». Уведомления служебные, но для необязательных видов ссылка отписки может понадобиться — вопрос для юриста.
7. Кыргызские тексты нового раздела нужно вычитать носителю языка.
