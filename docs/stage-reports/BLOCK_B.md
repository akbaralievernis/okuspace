# Отчёт: Блок B — Кабинет учителя

Дата: 2026-10-17. Ветка: `feat/block-b-grading` (от `feat/block-a-management`).

Основание — требование клиента. Учитель в своём кабинете:
- видит свои группы и учеников каждой группы;
- даёт задание всей группе или отдельному ученику;
- отмечает посещаемость;
- в конце месяца видит итог ученика с учётом экзамена (в классе или на сайте).

Решения — [ADR-0015](../DECISIONS.md), схема и правила расчёта — [SCHEMA.md §15](../database/SCHEMA.md).

## 1. Что сделано

| Требование | Реализация |
|---|---|
| Свои группы и ученики каждой группы | уже было (этапы 5–6): учитель видит только свои группы |
| Задание всей группе **или отдельным ученикам** | в форме задания — флажки учеников. Никто не отмечен — вся группа; отмечены — только они. Другие ученики (и их родители) задание не видят, не получают уведомление и не могут сдать |
| Посещаемость | уже было (этап 6). Теперь входит в итог месяца |
| Экзамен в классе | «Экзамены» в группе: название, дата, максимум. Баллы всем ученикам одной таблицей, отметка «не пришёл». Публикация отправляет уведомление ученику и родителям. Исправление после публикации пишется в аудит |
| Экзамен на сайте | любой онлайн-тест группы можно отметить «засчитывать как экзамен» |
| **Итог месяца без ручного заполнения** | «Журнал и итоги месяца»: по каждому ученику посещаемость, домашние, тесты, экзамены, итог и оценка — считает система. Учитель нажимает «Пересчитать», пишет комментарий и публикует. 1–3 числа черновики за прошлый месяц создаются сами, учитель получает уведомление |
| Ученик и родитель видят итоги | «Обучение → Итоги месяца и экзамены»: опубликованные итоги и баллы экзаменов (родитель — своих детей). Приходит уведомление |
| Правила школы | директор задаёт веса частей и шкалу («Панель → Правила итоговой оценки») |

**Значения по умолчанию** (клиент пока не ответил, меняются без программиста):
- веса: посещаемость 20%, домашние 30%, тесты 20%, экзамены 30%;
- шкала пятибалльная: от 90% — 5, от 75% — 4, от 60% — 3, ниже — 2.

**Правила расчёта:**
- не сданное после срока — 0;
- сданное, но не проверенное — пока не учитывается;
- уважительный пропуск не учитывается;
- если части за месяц нет (например, экзамена не было), её вес делится между остальными.

**Демо-данные** дополнены:
- экзамен с баллами в группе EN-A2;
- задание только для Эрлана;
- черновики итогов текущего месяца.

**Нестабильность e2e (честно).** Три прогона из семи упали частично: 18, 126 и 42 теста из 172. Все падения — `ECONNREFUSED`/`ERR_CONNECTION_RESET`: тестовый сервер на порту 3100 был недоступен. Ни одной ошибки в содержимом страниц. Вероятная причина: Playwright переиспользует уже запущенный сервер (`reuseExistingServer`), а тот ещё завершается после предыдущего прогона. Я это предполагаю, а не доказал. В CI сервер каждый раз новый. Если повторится — включу `reuseExistingServer: false` локально.

**Итог месяца сверен с ручным расчётом** на подготовленных данных прошлого месяца. Пример ученика:
- посещаемость 50% (1 из 2);
- домашние 80% (8 из 10);
- тест 90% (лучшая попытка из двух);
- экзамен 70%.

Итог 73% → оценка 3. Для второго ученика проверены:
- уважительный пропуск не считается;
- не сданное задание — 0;
- личное задание учтено только у него;
- «не пришёл» на экзамен — 0.

Итог 35% → оценка 2. Проверено также, что смена весов и шкалы директором меняет итог при пересчёте.

**Что ещё проверено тестами БД:**

- личное задание видят только адресат, учитель и руководство; родитель другого ученика — нет;
- чужой ученик не может сдать личное задание;
- уведомление получает только адресат;
- баллы экзамена: не больше максимума, только ученикам группы, вносит только учитель группы;
- до публикации экзамена ученик ничего не видит; после — только свой балл, родитель — балл своего ребёнка;
- опубликованный экзамен нельзя снять с публикации, удалить или изменить максимум;
- исправление балла записано в аудит;
- итоги считает только учитель группы или руководство; черновики ученику не видны;
- опубликованный итог не меняется ни пересчётом, ни комментарием, ни напрямую (даже служебной ролью);
- правила оценивания меняет только директор с MFA; сумма весов — ровно 100;
- черновики за прошлый месяц создаются 1–3 числа, а не в середине месяца; запустить это вручную пользователь не может.

**Мутационная проверка:** 21 из 21 мутации миграции поймана:

- адресаты игнорируются;
- ученик видит все задания;
- сдача чужого задания;
- уведомление всей группе;
- задание от чужого учителя;
- ученик не из группы;
- снятие экзамена с публикации;
- балл больше максимума;
- результаты видны до публикации;
- результаты чужих видны;
- правила без MFA;
- уважительный пропуск считается;
- не сданное не считается нулём;
- худшая попытка вместо лучшей;
- «не пришёл» не считается;
- сдвиг границы оценки;
- пересчёт любым пользователем;
- пересчёт опубликованного;
- опубликованный изменяем;
- черновики видны ученику;
- автосоздание в любой день.

Мутацию «сдвиг границы оценки» тесты сначала не ловили. Добавлен тест границ (90 / 89,99 / 75 / 74,99 / 60 / 59,99) — после этого она поймана.

## 4. Остающиеся проблемы и риски

1. **Шкала и веса не подтверждены клиентом** — стоят значения по умолчанию.
2. **На настоящем Supabase не проверено**; страницы с данными в браузере не проверены (в e2e нет БД).
3. Опубликованный итог нельзя исправить. Если клиенту это нужно — сделать «исправление с причиной» (новая версия).
4. Нет экспорта табеля в PDF и печатной формы.
5. Нет оценок за работу на уроке («активность»). Если клиент хочет — добавлю пятую часть итога.
6. Нестабильность локального e2e-сервера (см. выше).
7. Кыргызские тексты нужно вычитать носителю языка.
