# Отчёт: Этап 3 — Авторизация, роли и аккаунты

Дата: 2026-10-15. Ветка: `feat/stage-3-auth` (от `main` с этапом 2). Изменения не закоммичены.

## 1. Что сделано

**База данных — миграция `20261015100500_account_security`:**

- **MFA в БД.** Выдача, блокировка и отзыв ролей, приглашения, опекунство и создание организаций требуют `aal2`. Финансы требовали его ещё с этапа 2.
- **`accept_invitation(token)`.** Приглашение одноразовое и привязано к email из JWT. Функция проверяет срок, отзыв и то, что пригласивший *до сих пор* вправе выдать роль. На все отказы ответ одинаковый.
- **Директора приглашает только владелец платформы.**
- **Серверный rate limit:** `rate_limits` + `hit_rate_limit()`. Доступ только у service role, ключи хранятся как хеши.
- **`list_my_sessions()`** — список своих сеансов.
- **`consents`** — согласие на обработку ПДн записывается триггером при регистрации; append-only.
- **События о себе.** В `audit_logs.subject_profile_id` пишется, о ком событие; пользователь может читать записи о себе.

**Сервер** (`src/server/auth`, `src/server/authz`):

- Порты `AuthGateway`, `AccountRepository`, `RateLimiter` и их реализации на Supabase.
- Use cases: вход, регистрация, восстановление и смена пароля, ссылки из писем, MFA, выход, «завершить остальные сеансы», приглашение, принятие приглашения, блокировка, восстановление и отзыв роли.
- Server Actions.
- `requireUser` / `requireAccess`: серверная сессия через `getUser()`; привилегированные роли без MFA перенаправляются на `/mfa`.
- `proxy.ts` обновляет истёкшую сессию.

**Интерфейс** (ky/ru/en):

- вход, регистрация (с согласием), «забыли пароль», новый пароль, MFA (подключение по QR и ввод кода);
- кабинет;
- аккаунт: MFA, сеансы, события безопасности;
- сотрудники: приглашение с ролями по охвату; блокировка, восстановление и отзыв роли с подтверждением и причиной;
- страница приглашения.

**Документация:**

- обновлены [AUTH_FLOWS.md](../architecture/AUTH_FLOWS.md) и [SCHEMA.md](../database/SCHEMA.md).

## 4. Остающиеся проблемы и риски

1. **Реальный Supabase Auth не проверен.** Нет тестового проекта. Не проверены:
   - письма;
   - вход с настоящим паролем;
   - TOTP;
   - `verifyOtp`;
   - `signOut({scope:'others'})`;
   - чтение `auth.sessions` ролью `postgres`.

   Эти пути покрыты unit-тестами с поддельным шлюзом и e2e «без сервиса». Чек-лист — [SUPABASE_AUTH.md §7](../operations/SUPABASE_AUTH.md). **Обязателен до staging**, вместе с шлюзом этапа 2.
2. **Регистрацию нельзя открывать в production до этапа 4.** Текст согласия ссылается на политику конфиденциальности и правила, которых ещё нет. Ссылки на несуществующие страницы я сознательно не добавлял.
3. **Приглашения передаются ссылкой** (показывается один раз пригласившему), а не письмом. Письма — этап 11.
4. **Отзыв отдельного сеанса** не реализован — у Supabase нет публичного API. Есть «завершить все остальные».
5. **Подтверждение опасных действий** сделано через `window.confirm` + обязательную причину. Доступный диалог — этап 4 (дизайн-система).
6. **Кыргызские тексты** требуют вычитки носителем языка.
7. **Нагрузка.** `getUser()` в `proxy.ts` обращается к Auth на каждый запрос с cookie сессии. При росте нагрузки стоит перейти на `getClaims()` (локальная проверка JWT).
8. Dev-уязвимость `braces` — без изменений с этапа 1.
