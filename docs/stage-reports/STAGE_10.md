# Отчёт: Этап 10 — Мониторинг аудиторий (безопасный базовый уровень)

Дата: 2026-10-16. Ветка: `feat/stage-10-monitoring` (от `feat/stage-9-finance`).

## 1. Что сделано

Реализован **базовый уровень без видео**: платформа принимает от устройств только числа — сколько людей в аудитории и факт входа/выхода. Изображений, видео, лиц и биометрии в системе нет ни в схеме, ни в API ([ADR-0012](../DECISIONS.md), [SCHEMA.md §12](../database/SCHEMA.md)).

**Мониторинг выключен.** Включить его можно только после того, как указаны цель, правовое основание, опубликовано уведомление и отмечена юридическая проверка (ограничение в БД). Чек-лист для директора, юриста и установщика — [MONITORING_CHECKLIST.md](../operations/MONITORING_CHECKLIST.md).

| Требование | Реализация |
|---|---|
| Список камер и их состояние | устройства: тип (счётчик людей / вход-выход), статус, последние данные |
| Привязка к филиалу и аудитории | филиал обязателен, аудитория — из того же филиала (составной FK) |
| Связь аудитории с расписанием | каждое показание связывается с занятием в этой аудитории в этот момент |
| Подсчёт присутствующих | `occupancy_snapshots` (только число) |
| События входа и выхода | `zone_crossings` (только направление и время) |
| Сопоставление с расписанием, предупреждение об отсутствии группы | `monitoring_check`: «за всё занятие никого», «число людей расходится с отметками» (допуск ±2, с учётом преподавателя); одно предупреждение одного вида на занятие |
| Расхождения со списком записанных | в фактах предупреждения: максимум людей, замеры, записано в группу, отмечено присутствующими |
| Очередь сомнительных событий | «Очередь проверки»: подтвердить / ложное срабатывание — с обязательным комментарием, один раз, подпись проверяющего |
| Ручная корректировка посещаемости, история исправлений | через журнал занятия (этап 6): исправление сотрудником — с причиной, все версии в истории; данные камеры посещаемость не меняют |
| Отчёты по загрузке аудиторий | часы по расписанию, часы с людьми (интервалы 15 минут), средняя наполняемость занятий |
| Уведомления ответственным | уведомления в кабинете директору, менеджеру и администраторам филиала |
| Уведомление о видеонаблюдении | текст политики виден всем участникам школы; на главной кабинета — ссылка, когда мониторинг включён |
| Журнал просмотра | каждый просмотр показаний и отчёта о загрузке — запись в журнале доступа (append-only) |
| Срок хранения и удаление | данные до 90 дней, разобранные предупреждения 30–365 дней; удаляет только процедура хранения |
| Секреты интеграций | у каждого устройства свой случайный токен; в БД только SHA-256; показывается один раз; можно перевыпустить |

**Четыре уровня достоверности разделены:**

1. **Подсчёт людей** — без личностей.
2. **Пересечение входной зоны** — без личностей.
3. **Идентификация ученика** — только код занятия, карта доступа или преподаватель (этап 6). Событие камеры становится отметкой только после подтверждения человеком.
4. **Подтверждённая посещаемость** — решает человек.

Не реализованы и не планируются: распознавание лиц, анализ эмоций, «оценка внимания», автоматические наказания.

**Мутационная проверка:** 8 из 8 мутаций миграции пойманы:

- включение без юридических условий;
- приём без проверки токена;
- приём при выключенном мониторинге;
- дубли предупреждений;
- просмотр без записи в журнал;
- показания чужого филиала;
- удаление по сроку не работает;
- удаление сырых данных в обход процедуры.

## 4. Остающиеся проблемы и риски

1. **Юридическая проверка не проведена.** Закон КР о персональных данных, правовое основание, уведомления, согласие родителей несовершеннолетних, договор с поставщиком устройств — вопросы для юриста перечислены в чек-листе.
2. **Точность устройств не измерена.** Устройство не выбрано; допуск ±2 человека — предположение. Его нужно проверить на месте (порядок в чек-листе) и при необходимости изменить.
3. **Проверка занятий запускается вручную** («Проверить прошедшие занятия»). Запуск `monitoring_check` и `monitoring_purge` по расписанию — этап 13; до этого удаление по сроку не выполняется автоматически.
4. Нет предупреждения «устройство не передаёт данные»: вид заложен в схему, правило — вместе с планировщиком (этап 13).
5. Уведомления только в кабинете; email и мессенджеры — этап 11.
6. Отрисовка страниц с данными в браузере не проверена (в e2e нет БД).
7. Кыргызские тексты нового раздела нужно вычитать носителю языка.

## 6. Решение

**PASSED — по локальной проверке, кроме одного критерия.** Критерий «до запуска проверены юридические требования и реальная точность решения» — **BLOCKED**: он выполняется людьми на реальных устройствах. До этого мониторинг остаётся выключенным, и система не даёт его включить без отметки о юридической проверке. Остальные условия:

- прогон на реальном Supabase — до staging;
- планировщик проверок и удаления по сроку — этап 13.
